## 30 秒版

MiniFlow 是我做的一个「JSON 即工作流」的轻量自动化引擎：一张 JSON 描述节点和连线，引擎拓扑排序后逐个执行，支持 http / llm / agent / condition / code / template / delay 七种节点。重点不在"能跑"，而在"敢跑别人写的 JSON"——我给模板和代码节点做了双层沙箱，给 HTTP 节点做了 SSRF 防护，用 14 组真实攻击探针验证了 14/14 全部被拦或放行正确，包括模板原型链逃逸、constructor 链逃逸、死循环硬超时和 6 类 SSRF 地址。

## STAR 主线

**Situation（情境）**
低代码/自动化平台（n8n、Dify 这类）的核心是"用户写配置，平台代执行"。一旦平台执行的是不可信输入，两个高危面立刻出现：① 表达式/代码注入——恶意 JSON 里塞 `process.env` 或原型链逃逸，直接读走服务器密钥；② SSRF——HTTP 节点被用来打内网、打云元数据接口（169.254.169.254）偷临时凭证。

**Task（任务）**
做一个真实可用的工作流引擎，并把"执行不可信 JSON"的安全边界做扎实：沙箱逃逸要拦得住、死循环要杀得掉、内网地址要拦得住，同时公网正常业务不能误伤。

**Action（行动）**
- 引擎：Kahn 拓扑排序排执行序；连线可挂条件表达式；节点失败支持"容错继续"与"立即终止"两种策略。
- 沙箱：模板插值和 code 节点都跑在 `vm` 隔离上下文里，全局对象用 Proxy 包裹、注入对象递归包裹，切断 `constructor.constructor` 原型链；code 节点设 200ms/5s 硬超时（`MINIFLOW_SAFE_MODE` 可调）。
- SSRF：`assertSafeUrl` 在发起请求前校验目标——仅允许 http/https，拦截回环、localhost、私网段（10/8、192.168/16）、链路本地/云元数据地址。
- 验证：写了一个探针脚本，每项探针都真实创建工作流并触发运行，不是静态分析。

## 可能的追问与回答

- **"vm 沙箱不是号称不安全吗？"**
  对，社区共识是 `vm` 不能作为对抗高强度攻击的唯一防线。我的定位是防"配置层注入"（用户/租户级威胁模型），再加 Proxy 包裹切断最常见的原型链逃逸路径；真要对抗专职攻击者，应该用独立进程/容器隔离，这是我在 README 里写明的设计边界。
- **"14/14 是怎么保证不是脚本写错了？"**
  探针脚本第一版把 `run.results`（数组）误当 `run.nodes`（对象）解析，导致 6 项 SSRF 显示 `undefined` 被误判 LEAK——我发现"公网放行项"同样 undefined，说明是取数路径错而非防护失效，对照 `RunRecord` 类型修正后重跑才得到 14/14。测试脚本本身也要被怀疑。
- **"死循环 2018ms 和阈值 2000ms 的 18ms 差是什么？"**
  `vm` 超时是中断式触发，加上 HTTP 请求本身的开销，实测误差在 1% 以内，可接受。
- **"P50 亚毫秒是不是没意义？"**
  这是本机回环、排除网络因素的框架开销指标，说明路由和存储层（better-sqlite3）没有明显瓶颈；不代表生产网络延迟。

## 不能夸大的

1. 14/14 是"我设计的攻击面"全覆盖，不等于所有攻击面；沙箱边界已如实写明。
2. 接口延迟是回环指标，非生产环境数字。
3. LLM/Agent 节点未接真实大模型密钥做端到端，只验证了引擎编排与工具调用结构。
4. 死循环防住了同步死循环；异步挂起类任务靠外层超时，语义不同。
